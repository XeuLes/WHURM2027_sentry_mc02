# subControl 副板

本分支从 `main` 的 `ea7a02a` 建立，使用 MC02，配合 `mainControl` 工作目录中的 CAN3 v3 主控。
默认构建副板，不需要 `BOARD_ROLE`。在本目录运行 `mingw32-make -j4`，输出位于
`build/subControl/LuojiaFox_H7_Template.{elf,hex,bin}`。

## 分工与接线

主控负责遥控/上位机控制源、全机模式、底盘速度目标、大 Yaw 目标与过洞轨迹，直接驱动小云台和发射。
副板只执行底盘闭环、功率控制、超级电容控制和大 Yaw 闭环。

- CAN1：保留 main 的四台底盘 M3508 与超级电容配置。
- CAN2：保留 main 的大 Yaw DM4310 MIT 配置，ID 1、Master ID 0x51。
- CAN3：连接主控和枪口 DM-IMU，1 Mbit/s，标准经典 CAN。副板忽略 IMU 报文。
- 副板本地 BMI088 继续用于底盘反馈/补偿。大 Yaw 的绝对姿态来自主控 BMI088，通过 `0x311` 接收。

`.ioc`、`Core/Src/fdcan.c` 和 BSP CAN 配置保持 main 原样，自动重发关闭、TX FIFO。
CAN 终端电阻、接地和电机方向/机械零位仍须按实车验证；不把固件编译结果当作实机联调完成。

## 板间接口

完整接口见 [CAN3 v3 协议](CAN3_PROTOCOL.md)，两端 `board_link_can.hpp` 逐字一致。
设备层 `dvc_board_link_can` 负责 CAN 格式、序号及原始快照；应用层负责业务解码、时效和反馈合帧。

| ID | 方向 | 周期 | 字节 | 内容 |
| --- | --- | --- | --- | --- |
| 0x310 | 主→副 | 1 ms | 8 | 底盘系 vx/vy/wz、模式、有效位 |
| 0x311 | 主→副 | 1 ms | 8 | 大 Yaw 目标、BMI088 反馈/机械轨迹、使能和参考系 |
| 0x313 | 主→副 | 1 ms | 8 | 裁判功率上限、缓冲能量、两项年龄及有效位 |
| 0x31A | 副→主 | 1 ms | 8 | 底盘实测 vx/vy/wz、大 Yaw 机械偏角、独立有效位及 ready/低速位 |

不再使用 0x312、0x318、0x319。下行版本为 0x30；新反馈 ID 标识合并格式，须同时更新两板。
底盘目标 50 ms、大 Yaw 目标 20 ms 超时即停止对应输出；失能时仍发送心跳支持启动握手。
裁判年龄在副板继续累加，重复快照不把旧数据变新。源时效和超电原有功率逻辑保持不变。
IMU 模式使用主控 BMI088 实际航向和角速度；机械偏角模式使用副板电机位置/速度和主控轨迹参考。
副板只做闭环输出，不运行遥控、扫描或跟随目标状态机。
电机/CAN 输出故障锁定失能，需主控明确下发失能后清故障；断联本身不清故障。

## 偏角与底盘算法边界

副板回传大 Yaw 机械偏角。速度的坐标变换在主控进行：

- 遥控与上位机的平移目标均为枪口系，统一使用大 Yaw + 小 Yaw 相对底盘总偏角。
  SENTRY 中大 Yaw 系的速度约定不沿用，否则小 Yaw 偏转会导致上位机行驶方向错误。
- 两者都用 `vx_b = cos(a)*vx - sin(a)*vy`、`vy_b = sin(a)*vx + cos(a)*vy`；wz 不做平移旋转。
- 所需偏角无效时，主控下发无效底盘目标。副板直接使用收到的底盘系速度，不需要额外偏角下行帧。

`chassis_controller.cpp/.hpp`、`chassis_config.hpp`、运动/重力补偿、力分配和功率算法保留 main。
`app_chassis.cpp` 只将本地命令选择替换为主控目标输入，保留反馈→闭环→功率限制→电流发送顺序。
`chassis_power_manager.cpp` 和 `app_supercap.cpp` 只替换裁判快照来源，其算法不变。
旧主控相关源文件作为参考保留，通过构建列表排除；本固件不创建遥控、USB、裁判串口、发射控制任务。

## 验证范围

主/副板 ARM 固件编译与主机接口测试用于检查协议兼容、坐标方向、模式变化、断联、裁判年龄、
大 Yaw 握手和参考切换。大 Yaw 主机测试模拟电机接口，不证明实际力矩或控制稳定性。
六类 CAN3 消息全部按 1000 Hz 调度，含最坏位填充的预算为 81%。
DM 设备端仅开启加速度和角速度主动输出，主控独立解算枪口姿态，保留欧拉角/四元数接口。
此固件不写 DM 输出配置，实际设备设置和送达率需上板抓包确认。

## 底盘反馈与任务检查

副板在原 `readFeedback` 后发布速度快照，不改速度闭环或功率算法。全轮在线、估计有效、
数值有限且可编码时，1000 Hz 合并反馈中的底盘字段标有效；本地快照超过 10 ms 便标无效。
主控接收、校验并恢复 `system_state.chassis`，50 ms 没有新帧即失效。
USB `RobotMotion` 使用原 ID 0x08、原结构和 10 ms 周期，发送底盘系实测速度；无效时停发。
输入目标用枪口系，反馈保持原底盘系定义，主控不把目标回显当作实测值。

| 工作 | mainControl | subControl |
| --- | --- | --- |
| 遥控/USB 选择、模式与速度目标 | 执行 | 仅接收结果 |
| 枪口→底盘坐标转换、目标限幅 | 执行一次 | 不重复转换 |
| 轮电机反馈、底盘本地 IMU、原运动/重力补偿 | 不执行底盘闭环 | 保留原实现 |
| 速度 PID、力分配、电流输出 | 不执行 | 保留原实现 |
| 裁判解析 | UART 本地接收并转发年龄 | 接收快照 |
| 功率限制、超级电容控制 | 不执行 | 保留原实现 |
| 底盘速度遥测 | CAN 接收→USB 上报 | 发布实测速度 |

检查发现 main 原有 `ChassisPowerManager::resolveLimit()` 在裁判上限为 0 W 且超电给出正上限时，
`limit <= 0` 分支可能将上限重新抬高，与该函数“0 表示禁止输出”的注释不一致。
这属于已有功率逻辑问题；本次按底盘算法不修改的要求保留，未将其描述为已修复。
